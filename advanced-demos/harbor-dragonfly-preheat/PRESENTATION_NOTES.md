# Presentation notes: the fleet arrives after the disconnect

## Story

"We have one approved registry on site and five new workers. Pull-through caching
is too late if the first request arrives after the uplink disappears. Harbor
knows what we will deploy; let it seed the distribution tier first."

This is a fully scripted technical demo, not a production installation recipe.
The protagonist is a ~445 MB Jenkins LTS engine image (~253 MB compressed payload
in the measured run), not a tiny hello-world workload.

## Before going on stage

- Read the compatibility and isolation limits in [README.md](README.md).
- Reserve the two Compose project names and the network; do not share them with
  another presenter. Allow 25 GiB free space before acquiring the toolchain.
- Rehearse `./scripts/run-demo.sh` on the actual machine. First-run image
  acquisition can dominate time; the recorded complete cached-toolchain run
  took 182 seconds. Leave time for questions rather than promising that runtime
  on a different disk.
- Keep a previous run's private evidence elsewhere if needed. The orchestrator
  resets caches and destinations deliberately; do not "rehearse" by warming the
  benchmark destinations.
- Use one terminal, large font. The script clears only between CONNECTED and
  AIR-GAPPED, with short narration sleeps. Increase `DEMO_SLEEP_SECONDS` if needed.
- Do not show generated credential files. Raw diagnostic logs may contain
  operational metadata; review/redact before exporting evidence publicly.

## Key beats

1. **CONNECTED banner.** Point out the explicit pins and download boundary.
   Harbor configuration is generated by the official prepare image, not an
   incomplete reimplementation of its internal services.
2. **Harbor owns the preheat.** Explain provider `dragonfly`, exact Jenkins
   selectors and manual policy execution. Require one successful task, not
   merely HTTP 2xx or an empty policy execution.
3. **Seed evidence before consumers.** Show the seed's origin bytes and 13
   completed blob tasks. No consumer exists yet. The expected payload is
   measured from the selected amd64 manifest.
4. **AIR-GAPPED banner.** The network was internal from creation, but the host
   has now finished acquiring everything. Every container has one internal-only
   attachment; TCP 80/443 probes fail in each namespace.
5. **Direct baseline.** Five simultaneous fresh skopeo destinations show the
   central-registry pattern. Explain what the timer includes.
6. **Close the source.** All Harbor blob requests now return 403, even for the
   seed. Keep manifests and auth available so this remains a real registry
   image copy, not just an arbitrary file transfer.
7. **Five cold peers.** Each consumer has its own dfdaemon/cache and a client
   sharing its network namespace. No shared Docker image store or cached output
   can satisfy a copy.
8. **Show proof, then speed.** Manifest and all config/layer hashes match for
   all ten copies. The seed's origin counter is unchanged; the gate served zero
   successful blob bytes; peers uploaded pieces to each other.
9. **Do not sell a false speedup.** The final run was 7.52 s direct versus
   6.19 s P2P; the earlier run was 11.96 s versus 12.86 s. The reliable benefit
   is origin offload and surviving source denial. Real fleet speedups require
   a real topology/bottleneck test.

## Likely questions

**Is the whole laptop offline?** No. The host downloads artifacts during
CONNECTED; the workloads run on an internal Docker bridge. This is spectrum
level 3, not physically disconnected bootstrap or a hostile-user boundary.

**Does "no network" mean zero traffic?** No internet access. Local registry auth,
manifests, control-plane RPCs and P2P pieces are necessary. Negative probes are
intentional attempts and must fail.

**Why not stop Harbor entirely?** A normal pull still needs manifest and token
metadata. Blocking every blob is a stronger test of layer independence than
merely slowing Harbor down, without pretending metadata is unnecessary.

**Why skopeo instead of Docker-in-Docker?** It copies the complete real image
without privileged nested daemons, unpacking or host-daemon insecure-registry
changes. This measures cold OCI/distribution transfer, not workload startup.

**Is every container really a peer?** Five dfdaemon containers have independent
caches. Five skopeo clients join those namespaces and use each local proxy.
The seed is separate and was populated only through Harbor preheat.

**Does preheat guarantee availability later?** No. One rehearsal proved the
opposite: disk pressure evicted successfully preheated layers before consumers
arrived. Retention, sizing and monitoring are part of offline readiness.

**Why old Harbor/Dragonfly?** The selected versions implement a known, tested
legacy API contract. New Harbor uses authenticated Dragonfly job APIs.
The historical pair is deliberately unsuitable for production exposure.

**Where are TLS, signatures and the scanner?** Out of scope for this HTTP-only
distribution demo. They require a separate offline trust/update lifecycle;
SHA-256 matching a prepared manifest is not software provenance verification.

**Will Jenkins work offline?** This proves image distribution only. Plugin
catalogs, plugins, agents, build dependencies and update checks are independent
offline supply chains. Jenkins is not launched here.
